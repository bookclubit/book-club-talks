02Реляционная модель и SQL

Говорим «модель данных» — думаем

Эдгар Кодд 1923–2003

Математик из IBM. В 1970-м предложил реляционную модель — теорию, на которой стоит SQL. Премия Тьюринга — 1981.

А сам SQL?

1968 · иерархическая модель

IMS

Information Management System — СУБД IBM, сделанная для учёта запасов в программе «Аполлон». Первый коммерческий выпуск — 1968 год.

Данные — дерево записей: у каждой записи ровно один родитель. Связи «один-ко-многим» ложатся идеально, а «многие-ко-многим» — нет: общую запись приходится дублировать.

Чтобы найти данные, программа сама спускается по дереву сверху вниз. IMS жива до сих пор — на мейнфреймах IBM.

1970 · реляционная модель

Статья Кодда

«A Relational Model of Data for Large Shared Data Banks»: данные — отношения, то есть таблицы, и никаких путей доступа.

Главное отличие от IMS и CODASYL: вы говорите, что нужно, а не как до этого дойти. Путь к данным выбирает сама СУБД — позже эту работу назовут оптимизатором запросов.

На бумаге красиво, но в 1970 году это была теория: никто не знал, можно ли сделать такую базу быстрой.

1969–1970-е · сетевая модель

CODASYL

Комитет CODASYL — тот, что стандартизировал COBOL, — описал сетевую модель (отчёты DBTG 1969 и 1971 годов). Продукты — IDMS и другие.

Обобщение иерархии: у записи может быть несколько родителей, поэтому «многие-ко-многим» возможно. Но связи — это указатели, и программист сам ведёт курсор по пути доступа, как по связному списку.

В 1974 году на конференции ACM прошёл «Великий спор»: Кодд против Чарльза Бахмана, автора сетевого подхода. Реляционная модель в итоге победила.

середина 1980-х · стандарт

Реляционные СУБД (RDBMS) и SQL

RDBMS — relational database management system, система управления реляционными базами данных: программа, которая хранит таблицы и выполняет запросы на SQL.

Путь от статьи до продукта: проект System R в IBM (1974) и язык SEQUEL, позже SQL; Oracle — первая коммерческая SQL-СУБД (1979); IBM DB2 (1983); стандарт ANSI SQL (1986).

К середине 1980-х реляционные СУБД стали основным инструментом для всех, кому нужно хранить данные и делать к ним запросы.

System R ↗
Пример: Билл Гейтс и места работы
SELECT p.job_title, p.organization
FROM users u
JOIN positions p
  ON p.user_id = u.user_id
WHERE u.first_name = 'Bill'
  AND u.last_name = 'Gates';

-- Co-chair    | Gates Foundation
-- Co-founder  | Microsoft
конец 1980-х · объектная модель

Объектные базы данных

Идея: хранить объекты из кода как есть — без таблиц и ORM. Рассогласование кода и базы просто исчезает.

GemStone, ObjectStore, Versant, O2; в 1993 году появился общий стандарт ODMG.

Не взлетели: каждая база привязана к своему языку, нет общего языка запросов, а реляционные СУБД к тому времени уже стояли везде.

начало 2000-х · XML-модель

XML-базы данных

Время бума XML: веб-сервисы, конфиги, обмен данными. Появились базы, которые хранят XML-документы и отвечают на запросы XPath и XQuery: Tamino, eXist, MarkLogic.

Прижились в узкой нише — документооборот, издательства.

Главное наследие — тип XML в Oracle, SQL Server и PostgreSQL и стандарт SQL/XML: реляционные базы просто впитали идею.

2009 · семейство моделей

NoSQL

Не одна модель, а целое семейство: документные (MongoDB, CouchDB), ключ-значение (Redis, Riak, DynamoDB), широкие столбцы (Cassandra, HBase), графовые (Neo4j).

Общее — масштабирование на много машин и гибкая схема. Откуда взялось название и зачем всё это понадобилось — на следующем слайде.

2012 · не из главы

NewSQL

Ответ реляционного мира на NoSQL: SQL и транзакции остаются, но база работает на кластере из многих машин — как NoSQL.

Google Spanner (статья 2012 года) — одна база на весь мир, время синхронизируют атомные часы и GPS. Следом — CockroachDB, YugabyteDB, TiDB. Слово NewSQL придумал аналитик Мэттью Аслетт в 2011 году.

Spanner умеет хранить дочерние строки рядом с родительской — вернёмся к этому на слайде про локальность.

2012–2018 · не из главы

Сближение моделей

Модели перестали воевать и начали заимствовать друг у друга.

SQL берёт документы: PostgreSQL получил тип json (9.2, 2012) и jsonb с индексами (9.4, 2014), MySQL — JSON (5.7, 2015), стандарт SQL:2016 — функции для JSON.

Документы берут SQL: MongoDB научилась соединять коллекции через $lookup (3.2, 2015) и делать транзакции на несколько документов (4.0, 2018).

Подробнее о сближении — в конце доклада.

Пример: Билл Гейтс и места работы
-- PostgreSQL: документ внутри таблицы
CREATE TABLE users (id int, doc jsonb);

SELECT doc->'positions'
FROM users
WHERE doc->>'last_name' = 'Gates';

// MongoDB: соединение коллекций
db.users.aggregate([{ $lookup: {
  from: "positions",
  localField: "_id",
  foreignField: "user_id", as: "jobs" } }])
2023 · не из главы

Векторный поиск

Бум больших языковых моделей: понадобился поиск по смыслу, а не по точному совпадению. Текст превращают в вектор-эмбеддинг и ищут ближайшие векторы.

Сначала — отдельные векторные базы: Pinecone, Milvus, Weaviate. Затем то же самое появилось внутри привычных: расширение pgvector для PostgreSQL, векторный поиск в MongoDB Atlas, Redis, Elasticsearch.

История повторилась: новая модель стала ещё одним типом столбца.

pgvector ↗
Пример: Билл Гейтс и места работы
CREATE EXTENSION vector;
ALTER TABLE positions
  ADD embedding vector(1536);

-- чьи должности похожи на
-- «Co-founder, Microsoft»?
SELECT job_title, organization
FROM positions
ORDER BY embedding <-> (
  SELECT embedding FROM positions
  WHERE id = 457)
LIMIT 5;
2026 · не из главы

Сегодня

SQL снова в центре. PostgreSQL — самая используемая база в опросе разработчиков Stack Overflow с 2023 года.

Стандарт SQL:2023 добавил запросы к графам (SQL/PGQ), а в 2024-м вышел отдельный ISO-стандарт графового языка GQL. У NoSQL-баз появились SQL-подобные языки: CQL в Cassandra, SQL++ в Couchbase, PartiQL в DynamoDB.

Вывод главы подтвердился: не победитель, а соседство моделей.

Опрос Stack Overflow ↗
Пример: Билл Гейтс и места работы
-- SQL:2023, графовый запрос
-- прямо внутри SQL
SELECT org
FROM GRAPH_TABLE (resumes
  MATCH (u IS users
           WHERE u.last_name = 'Gates')
        -[IS worked_at]->
        (o IS organizations)
  COLUMNS (o.name AS org)

Справа, после 2009 года, — то, чего в главе нет: мы додумали сами.

Как показывать Полоски — схематичная иллюстрация, расположение блоков условное.

Текст Локальность выигрывает, только когда нужны большие части документа сразу. Базе обычно приходится загружать весь документ, даже если вам нужен маленький фрагмент. При обновлении тоже обычно переписывается весь документ, а «на месте» можно сделать только изменения, не меняющие закодированный размер. Поэтому рекомендуется держать документы маленькими и избегать записей, увеличивающих размер. Это заметно сужает круг случаев, где документные базы полезны.

В Oracle есть многотабличные кластеризованные таблицы, а семейства столбцов в модели Bigtable, которую используют Cassandra и HBase, тоже управляют локальностью.
