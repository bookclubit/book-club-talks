RSR vs SSR

Два отдельных процесса: один превращает компоненты в дерево элементов, другой — дерево в HTML. Наведите на узел, чтобы увидеть, как он выглядит на примере <div>Hi!</div>.

RSR — рендеринг серверных компонентов
SSR — серверный рендеринг
Серверные компоненты async function
Что это 
const App = async () => {
  return <div>Hi!</div>;
};

Обычная функция, которую можно ожидать через await. Её код остаётся на сервере и в бандл не попадает.

RSC-рендеринг
Дерево элементов React объект JavaScript
Что это 
{
  $$typeof: Symbol(react.element),
  type: "div",
  props: { children: "Hi!" }
}

Не HTML и не DOM, а описание того, каким должен быть DOM. Это данные — их можно инспектировать и сериализовать.

серверный рендеринг
HTML-поток строка / stream
Что это 
ReactDOMServer.renderToString(tree)
// → "<div>Hi!</div>"

Разметка, которую можно отдать по сети сразу — до того, как браузер скачает и выполнит JavaScript.

по сети
Клиент DOM + гидратация
Что это 
<div id="root"><div>Hi!</div></div>
hydrateRoot(document, <App />)

Браузер показывает готовую разметку, а React подключает к ней обработчики событий и динамику.

Наведите на конвейер — проявятся границы: где заканчивается RSR и начинается SSR

«По сути, серверные компоненты и серверный рендеринг можно рассматривать как два отдельных независимых процесса, где один процесс заботится исключительно о рендеринге компонентов на сервере и генерировании дерева элементов React, а другой процесс — серверный рендеринг — использует это дерево элементов React и преобразует его в HTML-разметку, которая может быть передана клиентам по сети.» Раздел «Серверный рендеринг», стр. 299

А что по коду?

Обычный express-сервер: раздаёт бандл, на любой маршрут собирает дерево, рендерит его в строку и отдаёт HTML. Нажмите на подсвеченную строку — справа появится пояснение. 

// server.js
const express = require("express");
const path = require("path");
const React = require("react");
const ReactDOMServer = require("react-dom/server");
const App = require("./src/App");

const app = express();


app.use(express.static(path.join(__dirname, "build")));



app.get("*", async (req, res) => {

  // Это секретный соус

  const rscTree = await turnServerComponentsIntoTreeOfElements(<App />);

  // Это секретный соус

  // Преобразуем ожидаемые серверные компоненты в строку

  const html = ReactDOMServer.renderToString(rscTree);


  // Отправим это
  res.send(`
    <!DOCTYPE html>
    <html>
      <head>
        <title>My React App</title>
      </head>
      <body>

        <div id="root">${html}</div>


        <script src="/static/js/main.js"></script>

      </body>
    </html>
  `);
});

app.listen(3000, () => {
  console.log("Server listening on port 3000");
});

Два процесса в пяти строках

Вся глава — про две строки в середине обработчика: сначала компоненты превращаются в дерево элементов, затем дерево — в HTML. Нажмите на подсвеченную строку, чтобы разобрать её отдельно.

Что делает turnServerComponentsIntoTreeOfElements

async function turnServerComponentsIntoTreeOfElements(jsx) {

  if (typeof jsx === "string" || typeof jsx === "number" ||
      typeof jsx === "boolean" || jsx == null) {
    return jsx;
  }



  if (Array.isArray(jsx)) {
    return await Promise.all(jsx.map(child => renderJSXToClientJSX(child)));
  }


  if (jsx != null && typeof jsx === "object") {

    if (jsx.$$typeof === Symbol.for("react.element")) {


      if (typeof jsx.type === "string") {
        return { ...jsx, props: await renderJSXToClientJSX(jsx.props) };
      }



      if (typeof jsx.type === "function") {
        const Component = jsx.type;
        const props = jsx.props;
        const returnedJsx = await Component(props);
        return await renderJSXToClientJSX(returnedJsx);
      }


      throw new Error("Not implemented.");

    } else {
      return Object.fromEntries(
        await Promise.all(
          Object.entries(jsx).map(async ([propName, value]) => [
            propName,
            await renderJSXToClientJSX(value),
          ])
        )
      );
    }

  }

  throw new Error("Not implemented.");
}

Большое дерево if/else

Рекурсивный обход JSX: примитивы — как есть, массивы — по детям, элементы React — по типу, всё остальное — по значениям пропсов. Нажмите на ветку, чтобы разобрать её.

шаг 1 из 5

Обработка входа: примитивы и массивы

Базовые случаи рекурсии — те условия выхода, без которых рекурсивный алгоритм не работает.

string / number / boolean / null →

Вернуть как есть. React понимает эти значения и на сервере, и на клиенте, и они сериализуемы — в отличие от функций и символов. В <div>hi!</div> дочернее «hi!» — просто строка, и должно остаться строкой.

Array.isArray(jsx) →

Promise.all(jsx.map(...)) — обработать каждый элемент рекурсивно и конкурентно. Если внутри массива несколько серверных компонентов делают независимые запросы, они выполняются параллельно, а не по очереди.

пример

Дочерний текст

<div>hi!</div>
// children: "hi!" → "hi!"
пример

Массив детей — и фрагменты заодно

[<div />, <h1 />, <span />, <Footer />]

<>…</> // фрагмент представляет детей массивом
«Идея состоит в том, чтобы возвращать типы объектов, которые React может понимать на стороне клиента и на стороне сервера. React может понимать и отображать строки, числа и логические значения как на стороне клиента, так и на стороне сервера, поэтому мы оставим их как есть.» Раздел «Под капотом», стр. 303

Сегодня: правила не изменились — React 19 одинаково рендерит строки, числа и массивы детей на сервере и клиенте, а конкурентная обработка через Promise.all осталась стандартным приёмом. В настоящем Flight-формате примитивы сериализуются нативно, без ручного обхода, но логика «вернуть как есть» сохранена.

Объекты: элемент React или просто пропсы?

Все элементы React — объекты, но не все объекты — элементы React. Критерий один: jsx.$$typeof === Symbol.for("react.element").

typeof jsx.type === "string" →

Встроенный DOM-элемент ("div", "span"): вернуть как есть, но рекурсивно обработать пропсы — внутри children могут прятаться серверные компоненты.

typeof jsx.type === "function" →

Пользовательский компонент (<Footer />): вызвать функцию с пропсами и запустить рекурсию на результате — пока не встретится базовый случай.

иначе — произвольный объект →

Обойти каждое значение пропсов рекурсивно. Так «бесплатно» поддерживается паттерн render props: компонент, переданный пропсом, тоже развернётся.

«Как мы узнаем, что объект является элементом React? У него есть свойство $$typeof со значением символа — в частности, Symbol.for("react.element"). Поэтому мы проверяем, имеет ли объект такую пару ключ/значение, и если да, то обрабатываем его как элемент React.» Раздел «Под капотом», стр. 304
«Мы делаем это потому, что элементы React могут иметь оба типа. Строки используются для встроенных элементов DOM, таких как "div", "span" и т. д. Функции применяются для пользовательских компонентов, таких как <Footer />.» Раздел «Под капотом», стр. 304–305

Сегодня: $$typeof — по-прежнему стабильная внутренняя конвенция React 19 (в том числе как защита от инъекций), дихотомия «строка — хост-элемент, функция — компонент» тоже. Добавились новые типы (ссылки на серверные действия, lazy-обёртки), а сам обход в продакшене выполняет Flight-рендерер React — руками такой код писать не нужно.

Главная суперсила: await Component(props)

клиентский React

Компонент не может быть async

// нельзя
async function MyComponent() {
  const data = await fetch(...);
  return <View data={data} />;
}

Рендерер ждёт синхронный результат, поэтому данные подтягиваются после первого рендера — через useEffect, Suspense, use().

на сервере

Можно просто ждать

const Component = jsx.type;
const returnedJsx = await Component(props);
return await renderJSXToClientJSX(returnedJsx);

Одно слово await перед вызовом — и серверный компонент может обращаться к базе, файловой системе или внешнему API прямо в теле.

Итог работы рендерера: дерево элементов, в котором нет «висящих» промисов и незагруженных данных — все зависимости разрешены до сериализации. Это принципиальное отличие от клиентской модели.

«Обратили внимание на await перед вызовом функционального компонента? Поскольку это выполняется на стороне сервера, мы можем асинхронно ожидать функциональный компонент в случае, если это серверный компонент! В этом и заключается волшебство серверных компонентов: мы можем асинхронно ожидать их на стороне сервера, и они вернут элемент React, который мы затем сможем передать в renderToString или поток, чтобы преобразовать его в направляемую клиенту строку или поток строк.» Раздел «Под капотом», стр. 305

Сегодня: асинхронные серверные компоненты — официальный паттерн React 19 и Next.js App Router (async function Page() с await db.query()). React 19 добавил хук use() для чтения промисов на клиенте, а «ждать всё до конца» превратилось в конкурентную модель: стриминг + границы Suspense отправляют готовые части сразу, не блокируя остальное.

Сериализация: элементы React → HTML-строки

Элемент React — ещё не DOM-узел, а инструкция, каким должен быть DOM. Сериализация превращает эти инструкции в разметку, пригодную для передачи по сети.

01

Быстрая первая отрисовка

Клиент получает готовую к отображению страницу и видит контент до того, как бандл скачается и выполнится — это прямо влияет на FCP и LCP.

02

Консистентность

Статичный HTML выглядит одинаково, отрисован он на сервере или на клиенте. Нет мерцания и сдвигов макета из-за расхождения двух рендеров.

03

Надёжная гидратация

Готовая разметка — прочная база: когда бандл загружен, React подключает обработчики событий и показывает динамику, а не рисует страницу заново.

пример 
const htmlString =
  ReactDOMServer.renderToString(element);

// → "<h1>Hello, world</h1>"
«Сериализация элементов React является фундаментальным аспектом обеспечения правильного и эффективного отображения вашего приложения при начальной загрузке, поскольку каждый вывод, отображаемый сервером, должен соответствовать клиентскому, чтобы React мог корректно согласовывать и дифференцировать данные.» Раздел «Сериализация», стр. 306

Сегодня: все три выгоды усилились — стриминговая отдача (renderToReadableStream + Suspense) шлёт HTML порциями, React 19 лучше диагностирует hydration mismatch, а гидратация стала частичной и приоритизированной. Терминология уточнилась: рендеринг в HTML (для первой отрисовки) и сериализация RSC payload / Flight (для передачи дерева) сегодня разделяют.

JSON.stringify не умеет сериализовать Symbol

// сериализация: Symbol → строка
JSON.stringify(element, (key, value) => {
  if (key === "$$typeof") return "react.element";
  return value;
});

// десериализация: строка → Symbol
JSON.parse(text, (key, value) => {
  if (key === "$$typeof") return Symbol.for("react.element");
  return value;
});

«И это всё! Теперь мы можем сериализовать и десериализовать элементы React»

В чём проблема

Элементы React — не обычные объекты: их опознаёт поле $$typeof, а его значение — Symbol. Символы не сериализуются: JSON.stringify просто теряет такое свойство, и клиентский React не распознает элементы.

«Несмотря на то что нам нужно сериализовать компоненты в строки, мы не можем просто использовать JSON.stringify, т. к. элементы React не являются обычными объектами JavaScript. Это объекты со специальным свойством $$typeof, которое React использует для их идентификации, и значением этих свойств является символ. Символы не могут быть сериализованы и отправлены по сети, поэтому нам нужно сделать что-то ещё.» Раздел «Сериализация», стр. 307

Сегодня: идея верна, реализация — учебная. Формально второй аргумент JSON.parse называется reviver (replacer — у stringify). В React 19 и Next.js дерево передаётся не через JSON, а стриминговым форматом Flight: он умеет промисы, Symbol-маркеры, циклические ссылки, ссылки на модули, серверные действия и BigInt — для JSON это было бы слишком.

Навигация: мягкие переходы вместо перезагрузки

старый мир

Полностраничная навигация

<a href="/bio">Bio</a>
// браузер запрашивает страницу целиком
// и сбрасывает всё состояние

Как в мире PHP: сервер рендерит страницу заново, браузер перерисовывает всё — отсюда «ощущение медлительности».

мир RSC

Мягкий переход

клик → запрос дерева JSX для маршрута
     → React перерисовывает страницу
     → состояние сохраняется

Полной перезагрузки нет: введённые данные, скролл и состояние клиентских компонентов остаются на месте. 

// один слушатель на window — делегирование событий
window.addEventListener("click", (event) => {
  if (event.target.tagName !== "A") return;
  event.preventDefault();
  navigate(event.target.href);
});

Почему делегирование

Вешать обработчик на каждую <a> дорого по памяти и медленно при большом числе ссылок: «большое количество слушателей может замедлить работу». Один слушатель на window проверяет цель клика и решает, перехватывать ли переход.

«Но мы можем добиться большего: с помощью RSC мы можем реализовать мягкую навигацию, при которой состояние сохраняется между переходами по маршруту. Мы делаем это, отправляя серверу URL, по которому хотим перейти, и сервер отправляет нам обратно дерево JSX для этой страницы. Затем React в браузере повторно отображает страницу с новым деревом JSX, и у нас будет новая страница без обновления всей страницы.» Раздел «Навигация», стр. 308

Сегодня: мягкая навигация — стандарт: в Next.js App Router её делают <Link> и useRouter, в React Router v7 и TanStack Start — их аналоги. Делегирование по-прежнему валидно, а рядом появились Navigation API и View Transitions API. В продакшене добавляются предзагрузка соседних маршрутов, кэш и дедупликация запросов.

navigate(): fetch → десериализация → root.render()

// клиент

async function navigate(url) {
  const response = await fetch(url, {
    headers: { "jsx-only": true },
  });



  const element = JSON.parse(await response.text(), (key, value) => {
    if (key === "$$typeof") return Symbol.for("react.element");
    return value;
  });



  root.render(element);
}


// корень получаем при первоначальной гидратации

const root = hydrateRoot(document, <App />);

Публичный API, а не хак

Вся «магия» навигации собрана из официальных API: fetch, JSON.parse с reviver и root.render(). Нажмите на шаг, чтобы разобрать его отдельно.

«Мы получаем корень от React при первоначальной гидратации страницы и можем использовать этот root для отображения в него новых элементов. Вот так работает React "под капотом". Мы просто применяем тот же API, который React использует внутри. Это хорошо: значит, мы не делаем ничего особенного или хакерского, мы просто используем общедоступный API React.» Раздел «Навигация», стр. 309

Сегодня: hydrateRoot и root.render() — актуальные API React 19. В реальных приложениях навигацией управляет фреймворк: <Link prefetch>, router.push, Router Cache и инкрементальные обновления RSC payload вместо ручного fetch.

Серверная сторона: заголовок «jsx-only»

Один и тот же маршрут app.get("*") обслуживает два сценария и различает их по наличию заголовка.

заголовка нет

Первая загрузка

rscTree → renderToString → HTML-шаблон
<!DOCTYPE html> … <div id="root">…</div>
<script src="/static/js/main.js">

Полный конвейер: дерево, разметка, каркас страницы и бандл.

jsx-only: true

Мягкая навигация

res.end(JSON.stringify(rscTree, replacer))
// без HTML-обёртки и без renderToString

Этап HTML пропускается: у клиента уже есть работающее приложение, ему нужно только новое дерево.

Почему строка, а не объект

Ответ отправляется строкой, потому что на клиенте вызывается JSON.parse, а он ожидает строку. Отправь сервер готовый объект — пришлось бы лишний раз сериализовать и разбирать. Это особенность API, а не архитектурный выбор.

«Вы обратили внимание, что при наличии этого заголовка мы отправляем не JSON, а просто строку? Делаем мы так потому, что нам нужно выполнить JSON.parse на стороне клиента, а JSON.parse ожидает строку, а не объект JSON. Это всего лишь особенность API, но это не так уж и плохо.» Раздел «Навигация», стр. 310

Сегодня: согласование по заголовкам живо и масштабировано — Next.js различает запросы по RSC: 1, Next-Router-Prefetch, Next-Router-State-Tree. Формат ответа — не JSON-строка, а стриминговый Flight-поток: он эффективнее на больших страницах и умеет Suspense.

Не всё может быть серверным: пример Counter

function Counter() {
  const [count, setCount] = useState(0);

  return (
    <div>
      <p>Count: {count}</p>
      <button onClick={() => setCount(count + 1)}>+</button>
    </div>
  );
}

useState — API только клиента

Сервер не знает начальное значение count для конкретного пользователя, а «состояние» в серверной среде разделяется многими клиентами — это путаница данных и риск раскрыть чужое. Вдобавок setState — функция, а функции не сериализуемы.

onClick — серверы не интерактивны

«Нельзя щёлкнуть по запущенному процессу на сервере», поэтому обработчик события в серверном компоненте — невозможное состояние. Пропсы серверных компонентов должны быть сериализуемы, а функция — нет.

«Этот компонент никогда не сможет быть серверным по двум причинам. Он использует useState, который является API только клиентской части. … Этот компонент использует onClick, который имеет смысл только для API клиентской части. Это связано с тем, что серверы не интерактивны: вы не можете щёлкнуть по запущенному процессу на сервере, поэтому onClick в серверных компонентах — это что-то вроде невозможного состояния.» Раздел «Внесение обновлений», стр. 311–312

Сегодня: ограничения закреплены в документации React 19 — useState, useEffect и обработчики событий в серверных компонентах недоступны. Легальный обход для «поведения» — серверные действия ("use server"): функция не передаётся значением, а превращается в ссылку на серверный endpoint.

Разделяй и властвуй: ServerCounter + клиентская часть

// ServerCounter.js — серверный компонент
function ServerCounter() {
  return (
    <div>
      <h1>Hi friends, look at my nice counter!</h1>
      <p>About me: I like to count things…</p>
      <InteractiveClientPart />
    </div>
  );
}

// InteractiveClientPart.js
"use client";

function InteractiveClientPart() {
  const [count, setCount] = useState(0);
  return (
    <>
      <p>Count: {count}</p>
      <button onClick={() => setCount(count + 1)}>+</button>
    </>
  );
}

В бандл уезжает только интерактивное

Заголовок, абзац и разметка остаются на сервере и в клиентский JavaScript не попадают вообще. Пользователь скачивает крошечный фрагмент — счётчик и кнопку.

сеть

Меньше данных — быстрее первая загрузка, особенно на медленном соединении.

процессор

Меньше JS парсить и выполнять — быстрее интерактивность, меньше расход батареи.

«Мы только что выделили крошечную часть нашего приложения, которая должна быть интерактивной, и только эта часть приложения на самом деле будет доступна нашим пользователям как часть пакета JavaScript, а остальное — нет. Как следствие, мы отправляем по сети пакеты JavaScript значительно меньшего размера, что означает более быструю загрузку и более высокую производительность для наших пользователей как с точки зрения ресурсов процессора, так и с точки зрения сети.» Раздел «Внесение обновлений», стр. 312–313

Сегодня: «максимум на сервере, минимум на клиенте» — официальная рекомендация: в Next.js компоненты серверные по умолчанию, клиентскими их делает "use client". React Compiler уменьшает клиентский код автоматической мемоизацией, но физическое исключение серверного кода из бандла даёт больший эффект, чем любая оптимизация.

«Когда вы дойдёте до этой точки в дереве, настанет время использовать вот этот конкретный модуль»

Дыры, которые заполняет клиент

Сервер отрисовывает целое дерево и оставляет только «дыры» — ссылки на клиентские модули. Клиентский React находит их и подставляет реальные модули из бандла. Серверные компоненты при этом можно оборачивать в Suspense: фреймворк отдаёт их по мере готовности данных.

«Компонент InteractiveClientPart является клиентским компонентом, поэтому он не отображается на сервере. Вместо этого сервер отображает заполнитель для клиентского компонента, который является ссылкой на конкретный модуль, созданный компоновщиком клиентского пакета.» Раздел «Что "под капотом"?», стр. 313–314

Сегодня: директивы "use client" и "use server" документированы в React 19; ссылки на модули существуют именно так и передаются во Flight-потоке с идентификаторами сборщика (Turbopack, webpack, Vite). Предзагрузка и приоритизация клиентских модулей — стандартная практика.

Клиентские компоненты тоже выполняются на сервере

«Выполнить компонент» — значит вызвать его функцию с пропсами и получить элемент React. Не «стать интерактивным в браузере», а просто вызвать функцию.

✓

Серверные компоненты выполняются на сервере → объекты элементов.

✓

Клиентские компоненты выполняются на сервере → тоже объекты элементов.

✓

На сервере получается единый большой объект всех элементов — и клиентских, и серверных.

✓

Этот объект превращается в строку и отправляется клиенту.

✕

Серверные компоненты никогда не выполняются на клиенте — их код туда не попадает.

✓

Клиентские компоненты с этого момента выполняются исключительно на клиенте.

«Существует распространённое заблуждение, будто серверные компоненты выполняются только на сервере, а клиентские — только на клиенте. Это не совсем так. … Во время серверного рендеринга клиентские компоненты выполняются на сервере и выводят объекты, представляющие элементы React. Затем эти элементы преобразуются в строку HTML и отправляются клиенту, где браузер отображает HTML-разметку.» Раздел «Нюансы», стр. 316–317

Сегодня: модель каноническая и в 2026-м. Отсюда практика: не трогать window и localStorage в теле клиентского компонента (только в useEffect), помнить о двойном рендере при работе с датами и случайными числами. Исключения вроде отключённого SSR — конфигурация, а не правило.
