Социальный граф

Текст Граф состоит из двух типов объектов. Вершины, они же узлы или сущности. И рёбра, они же связи или дуги. На граф ложатся многие данные. Социальные графы: вершины — люди, рёбра — знакомства. 07Графы свойств

Из чего состоят вершина и ребро

Вершина

Уникальный ID · исходящие рёбра · входящие рёбра · свойства «ключ — значение»

Ребро

Уникальный ID · начальная и конечная вершины · метка связи · свойства «ключ — значение»

Текст В модели графов свойств каждая вершина состоит из уникального идентификатора, множества исходящих рёбер, множества входящих рёбер и коллекции свойств — пар «ключ — значение». Каждое ребро — из уникального идентификатора, вершины, с которой оно начинается, вершины, которой заканчивается, метки, описывающей вид связи, и своей коллекции свойств.

Как показывать Свойство year у ребра — моя иллюстрация того, что у рёбер тоже бывают свойства.

Переход Граф свойств легко представить в виде… двух обычных таблиц.

08Граф в двух таблицах

Граф свойств — это две таблицы

CREATE TABLE vertices (    vertex_id   integer PRIMARY KEY,    properties  json);CREATE TABLE edges (    edge_id     integer PRIMARY KEY,    tail_vertex integer REFERENCES vertices (vertex_id),    head_vertex integer REFERENCES vertices (vertex_id),    label       text,    properties  json);CREATE INDEX edges_tails ON edges (tail_vertex);CREATE INDEX edges_heads ON edges (head_vertex);
  • 01Любая вершина соединяется с любой: схема не ограничивает
  • 02Обход в обе стороны: для этого два индекса
  • 03Метки: разные виды связей в одном графе

Текст Графовое хранилище можно представить как две реляционные таблицы: одна для вершин, другая для рёбер. Свойства здесь лежат в типе json СУБД PostgreSQL. Для каждого ребра хранится начальная и конечная вершины, поэтому получить входящие или исходящие рёбра вершины — запрос к head_vertex или tail_vertex.

Текст Важны три аспекта. Первое: любая вершина может быть соединена ребром с любой другой, схема не ограничивает связи. Второе: для любой вершины можно найти и входящие, и исходящие рёбра, то есть обойти граф в обоих направлениях; поэтому индекс есть на обоих столбцах. Третье: разные метки позволяют хранить в одном графе разные виды информации, сохраняя чистоту модели.

10Язык Cypher

Запрос рисует граф стрелочками

Создан для Neo4j ↗. Назван в честь персонажа «Матрицы», а не шифра

CREATE  (NAmerica:Location {name:'North America', type:'continent'}),  (USA:Location      {name:'United States', type:'country'  }),  (Idaho:Location    {name:'Idaho',         type:'state'    }),  (Lucy:Person       {name:'Lucy' }),  (Idaho) -[:WITHIN]->  (USA)  -[:WITHIN]-> (NAmerica),  (Lucy)  -[:BORN_IN]-> (Idaho)

Текст Cypher — декларативный язык запросов для графов свойств, созданный для Neo4j. Кстати, получил название в честь персонажа «Матрицы» и к шифрам отношения не имеет.

Текст Это вставка левой части рисунка. Каждой вершине дано условное название, USA или Idaho, и дальше они соединяются стрелочной нотацией: Idaho, ребро WITHIN, USA. Читается почти как картинка.

11Кто эмигрировал из США в Европу

Условие на два пути от одной вершины

MATCH  (person) -[:BORN_IN]->  () -[:WITHIN*0..]-> (us:Location {name:'United States'}),  (person) -[:LIVES_IN]-> () -[:WITHIN*0..]-> (eu:Location {name:'Europe'})RETURN person.name

Текст После вставки всех вершин можно спрашивать интересное: найти имена всех людей, эмигрировавших из США в Европу. То есть вершины, ребро BORN_IN которых указывает на место в США, а ребро LIVES_IN — на место в Европе.

Текст Читаем запрос. Найти все вершины person, у которых есть исходящее ребро BORN_IN к какой-либо вершине, а из неё можно по цепочке рёбер WITHIN дойти до Location с именем United States. И у той же вершины есть LIVES_IN, откуда по цепочке WITHIN можно дойти до Europe. Вернуть имя. Запись WITHIN*0.. значит «следуй по ребру ноль или более раз», как звёздочка в регулярных выражениях.

Как показывать Зелёным подсвечивается путь рождения Люси, красным — путь проживания. Это пример 2.4, с. 80.

13Графовые запросы в SQL

В графе число соединений неизвестно заранее

LIVES_IN может указывать
  • На улицу
  • На город
  • На область
  • На штат или страну
() -[:WITHIN*0..]-> () -- следуй по WITHIN ноль или более раз-- как оператор * в регулярках
В SQL
Можно с SQL:1999: рекурсивные обобщённые табличные выражения, WITH RECURSIVE ↗

Текст Да, запросы графа можно выполнять на SQL, хотя и не без проблем. В реляционной базе нужные соединения обычно известны заранее. А в графовом запросе может понадобиться обойти неизвестное число рёбер. Ребро LIVES_IN может указывать на улицу, город, область, штат, и до искомой вершины может быть несколько уровней иерархии.

Текст В Cypher это отражено буквально: WITHIN*0... В SQL начиная с SQL:1999 это можно выразить рекурсивными обобщёнными табличными выражениями, синтаксисом WITH RECURSIVE. Его поддерживают PostgreSQL, DB2, Oracle и SQL Server.

Как показывать Сегодня в стандарте SQL:2023 есть и прямые графовые запросы: SQL/PGQ.

14Тот же запрос

Один вопрос: 4 или 29 строк

Cypher
MATCH  (person) -[:BORN_IN]->  ()    -[:WITHIN*0..]-> (us {name:'United States'}),  (person) -[:LIVES_IN]-> ()    -[:WITHIN*0..]-> (eu {name:'Europe'})RETURN person.name
Вывод
Разные модели созданы для разных задач. Выбирайте подходящую
SQL с WITH RECURSIVE · без комментариев
WITH RECURSIVE  in_usa(vertex_id) AS (      SELECT vertex_id FROM vertices WHERE properties->>'name' = 'United States'    UNION      SELECT edges.tail_vertex FROM edges        JOIN in_usa ON edges.head_vertex = in_usa.vertex_id        WHERE edges.label = 'within'  ),  in_europe(vertex_id) AS (      SELECT vertex_id FROM vertices WHERE properties->>'name' = 'Europe'    UNION      SELECT edges.tail_vertex FROM edges        JOIN in_europe ON edges.head_vertex = in_europe.vertex_id        WHERE edges.label = 'within'  ),  born_in_usa(vertex_id) AS (    SELECT edges.tail_vertex FROM edges      JOIN in_usa ON edges.head_vertex = in_usa.vertex_id      WHERE edges.label = 'born_in'  ),  lives_in_europe(vertex_id) AS (    SELECT edges.tail_vertex FROM edges      JOIN in_europe ON edges.head_vertex = in_europe.vertex_id      WHERE edges.label = 'lives_in'  )SELECT vertices.properties->>'name'FROM verticesJOIN born_in_usa     ON vertices.vertex_id = born_in_usa.vertex_idJOIN lives_in_europe ON vertices.vertex_id = lives_in_europe.vertex_id;

Текст Тот же самый запрос — эмигранты из США в Европу — на SQL с рекурсивными выражениями. Сначала множество мест в США: начинаем с вершины United States и добавляем всё, что входит по рёбрам within. То же самое для Европы. Затем ищем родившихся в США и живущих в Европе. И наконец пересекаем эти множества соединением.

Текст Один и тот же запрос пишется в четыре строки на одном языке и требует двадцати девяти на другом. Это показывает, что разные модели данных адаптированы для разных сценариев. Поэтому важно выбрать подходящую для вашего приложения.

Как показывать Это примеры 2.4 и 2.5 (с. 80, 82). В книге Cypher занимает 4 строки: на слайде первые две длинные строки перенесены, чтобы поместились в колонку. SQL показан без комментариев: это те самые 29 строк.

15Хранилища тройных кортежей

Всё — это трёхсловное высказывание

СубъектДжим
Предикатлюбит
Объектбананы
Объект — значение

(lucy, age, 33) = вершина lucy со свойством {"age": 33}

Объект — другая вершина

(lucy, marriedTo, alain) = ребро с меткой marriedTo между двумя вершинами

Текст Модель тройных кортежей практически эквивалентна графу свойств: другие слова для тех же идей. Но её стоит обсудить, потому что вокруг неё свои инструменты и языки.

Текст Вся информация хранится в виде простых высказываний: субъект, предикат, объект. Джим любит бананы. Субъект эквивалентен вершине. А объект — одно из двух. Либо значение простого типа: тогда предикат и объект — ключ и значение свойства. Либо другая вершина: тогда предикат — это ребро. Возраст и брак Люси пишутся одинаково.

Вершина. Имя нужно лишь внутри файла, чтобы понять, какие кортежи к ней относятся

Экономит повторы субъекта. Это и делает Turtle приятным для чтения

Текст Вот те же данные в формате Turtle, подмножестве Notation3. Вершины записаны как _:название, и это название ничего не значит за пределами файла. Если предикат — ребро, объект — вершина: _:idaho :within _:usa. Если свойство — строка: _:usa :name "United States".

Переход С тройными кортежами часто всплывает семантическая паутина.

17Семантическая паутина

Идея не взлетела, а кортежи пригодились

Идея

Сайты публикуют данные и для людей, и для машин: в едином формате RDF ↗. Получается «всеобщая база данных»

Реальность

В начале 2000-х её переоценили. На практике её не реализовали: обилие аббревиатур и слишком сложные стандарты

Что осталось

Тройные кортежи — неплохая внутренняя модель приложения, даже без публикации RDF

Деталь
Предикаты в RDF — это URI: <http://my-company.com/namespace#within>. Так ваше within не конфликтует с чужим

Текст Модель тройных кортежей независима от семантической паутины: например, Datomic о ней вообще не упоминает. Но в представлении многих они связаны. Идея простая: сайты публикуют информацию для людей, почему бы не публиковать и для компьютеров? RDF был задуман как механизм, чтобы данные разных сайтов автоматически объединялись в паутину данных, всеобщую базу.

Текст Значение этой идеи сильно переоценили в начале 2000-х, а на практике она не реализована: автор упоминает головокружительное обилие аббревиатур и слишком сложные стандарты. Но модель осталась полезной.

Текст Особенность RDF — нацеленность на обмен в масштабе интернета. Поэтому предикаты часто записаны как URI: тогда ваш within не конфликтует с чужим. Такой URL необязательно должен открываться, это просто пространство имён.

Cypher заимствовал поиск по шаблону у него

PREFIX : <urn:example:>SELECT ?personName WHERE {  ?person :name ?personName.  ?person :bornIn  / :within* / :name "United States".  ?person :livesIn / :within* / :name "Europe".}
(person) -[:BORN_IN]-> () -[:WITHIN*0..]-> (location)# Cypher
?person :bornIn / :within* ?location.# SPARQL

Текст SPARQL — язык запросов для хранилищ тройных кортежей с моделью RDF. Аббревиатура: SPARQL Protocol and RDF Query Language, произносится как «спаркл». Он предшествовал Cypher, поиск по шаблону в Cypher заимствован отсюда, поэтому они так похожи.

Текст Тот же запрос про эмигрантов получается даже короче. Выражения почти совпадают. А поскольку RDF не различает свойства и рёбра, для свойств используется тот же синтаксис. Автор называет SPARQL прекрасным языком: семантическая паутина не случилась, но для внутреннего использования он отлично подходит.

Текст В первом докладе мы говорили о CODASYL. На первый взгляд, сетевая модель похожа на графовую. Может, графовые базы — завуалированное второе пришествие CODASYL? Автор отвечает: нет. Отличий четыре.

Текст В CODASYL схема определяет, какие типы записей могут быть вложены в какие; в графе любая вершина соединяется с любой. В CODASYL до записи можно добраться только по пути доступа; в графе можно сослаться прямо по ID или использовать индекс. В CODASYL потомки — упорядоченное множество, база поддерживает порядок, а приложение о нём заботится; в графе вершины и рёбра не упорядочены. В CODASYL все запросы императивны и легко ломаются; в графе есть высокоуровневые языки.

20Фундамент: Datalog

Сначала факты, потом правила

Изучался в вузах в 1980-х. Подмножество Prolog. Запись: предикат(субъект, объект)

Факты
name(namerica, 'North America').type(namerica, continent).name(usa, 'United States').within(usa, namerica).name(idaho, 'Idaho').within(idaho, usa).name(lucy, 'Lucy').born_in(lucy, idaho).
Правила
/* Правило 1 */within_recursive(Location, Name) :-    name(Location, Name)./* Правило 2 */within_recursive(Location, Name) :-    within(Location, Via),    within_recursive(Via, Name).

Текст Datalog гораздо старше Cypher и SPARQL, его широко изучали в вузах в 1980-х. Среди разработчиков он не так известен, но важен как фундамент последующих языков. На практике используется немногими: это язык запросов Datomic, а Cascalog — реализация Datalog для Hadoop.

Текст Модель похожа на тройные кортежи, только запись другая: предикат(субъект, объект). Но ход мысли другой. Cypher и SPARQL сразу начинают с SELECT, а Datalog движется мелкими шагами. Сначала описываем правила, которые определяют новые предикаты. Слова с большой буквы — переменные. Правило работает, если нашлись соответствия для всего справа от :-. Правила могут ссылаться друг на друга и на себя, как функции.

Как показывать Факты немного сокращены, полный вид — пример 2.10 на с. 88.

21Рис. 2.6

Факт про Айдахо выводится, а не записан

Текст Один из возможных способов применения правил. Кортеж name(namerica, North America) есть в базе, значит, работает правило 1: появляется within_recursive(namerica, North America). Дальше within(usa, namerica) есть в базе, а предыдущий факт мы только что получили, значит, работает правило 2: within_recursive(usa, North America). И наконец within(idaho, usa) плюс этот факт дают within_recursive(idaho, North America).

Текст Многократно применяя правила 1 и 2, получаем все места в Северной Америке или где угодно ещё. В базе нигде не записано, что Айдахо находится в Северной Америке: система вывела это сама.

22Запрос на Datalog

Правила можно комбинировать

/* Правило 3 */migrated(Name, BornIn, LivingIn) :- name(Person, Name),                                    born_in(Person, BornLoc),                                    within_recursive(BornLoc, BornIn),                                    lives_in(Person, LivingLoc),                                    within_recursive(LivingLoc, LivingIn). ?- migrated(Who, 'United States', 'Europe')./* Who = 'Lucy'. */
Плюс

Правила переиспользуются в разных запросах, полезно на сложных данных

Минус

Другое мышление, и для простых разовых запросов это менее удобно

Текст С помощью правила 3 можно найти людей, родившихся в BornIn и живущих в LivingIn. Спрашиваем с BornIn равным United States и LivingIn равным Europe, а людей оставляем переменной Who: система находит значения этой переменной. Результат тот же, что у Cypher и SPARQL: Люси.

Текст Datalog требует другого мышления. Для простых разовых запросов это менее удобно, но весьма полезно при сложных данных, потому что правила можно комбинировать и использовать повторно.

Общая черта документных и графовых баз — нет обязательной схемы. Но приложение всё равно предполагает структуру; вопрос в том, явная она или неявная.
