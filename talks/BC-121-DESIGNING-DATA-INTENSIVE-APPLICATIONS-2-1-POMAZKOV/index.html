Текст Самая известная модель — модель данных SQL. Её основа — реляционная модель, которую Эдгар Кодд предложил в 1970 году: данные организованы в отношения, в SQL это таблицы, а каждое отношение — неупорядоченный набор кортежей, то есть строк.

Текст Это была теоретическая конструкция, и многие сомневались, что её можно эффективно реализовать. Но к середине 1980-х реляционные СУБД и SQL стали основным инструментом для всех, кому нужно хранить более или менее структурированные данные и выполнять запросы. Господство длилось 25–30 лет — целая вечность для нашей отрасли.

05Рождение NoSQL

Название появилось из хештега, а причины настоящие

Масштаб

Большие наборы данных и высокая пропускная способность по записи

Свобода

Свободное ПО вместо коммерческих продуктов

Запросы

Специальные операции, плохо поддержанные реляционной моделью

Схема

Усталость от жёстких схем, нужны более динамичные модели

Будущее
Не победитель, а соседство: polyglot persistence — несколько систем хранения в одном приложении

Текст NoSQL — название неудачное: оно ничего не говорит о технологии. В 2009 году это был просто броский хештег в Twitter для семинара по распределённым нереляционным базам с открытым кодом. Термин задел за живое, и задним числом его расшифровали как Not Only SQL.

Текст Причин для внедрения четыре: потребность в большем масштабировании, предпочтение свободного ПО, специальные запросы, которые плохо ложатся на реляционную модель, и разочарование ограниченностью схем.

Текст Вывод автора: у каждого приложения свои требования, и реляционные базы будут жить рядом с нереляционными. Это называют polyglot persistence.

Переход Теперь конкретная боль, из-за которой на SQL ругаются чаще всего. И нам, разработчикам, она знакома лично.

Источники Polyglot persistence.

06Рассогласование

Код думает объектами, база — строками

Impedance mismatch — термин из электроники: при несовпадении импедансов сигнал отражается

В коде
user = {  name: "Bill",  positions: [ … ],  education: [ … ],}
⇄
ORMнеуклюжий слой
В базе
userspositionseducationcontact_inforegionsindustries
Значит
ActiveRecord ↗ и Hibernate ↗ сокращают шаблонный код, но не скрывают разницу между моделями

Текст Большая часть кода сегодня объектно-ориентированная, и отсюда главная критика SQL: между объектами в коде и таблицами, строками и столбцами нужен неуклюжий промежуточный слой. Эту расстыковку называют impedance mismatch, рассогласование. Термин из электроники: при соединении цепей мощность передаётся лучше всего, когда импедансы совпадают; иначе сигналы отражаются.

Текст ORM-фреймворки — ActiveRecord, Hibernate — сокращают количество шаблонного кода, но полностью скрыть разницу между моделями не могут. Посмотрим на примере.

Одно резюме — шесть таблиц

Поля «по одному» — столбцы. Всё, чего много, — отдельная таблица со ссылкой на user_id

Другие варианты
структурные типы и JSON прямо в столбце · текст с JSON, но запросов к нему нет

Текст Вот резюме из LinkedIn, профиль Билла Гейтса. У него есть уникальный user_id. Имя и фамилия встречаются ровно один раз — это столбцы таблицы users. Но должностей за карьеру больше одной, мест учёбы и контактов тоже. Это связь «один-ко-многим».

Текст В классическом нормализованном виде должности, образование и контакты уходят в отдельные таблицы со ссылкой на users через внешний ключ. Позже в SQL-стандарт добавили структурные типы и XML, а затем и JSON: многоэлементные данные можно хранить в одной строке и даже делать к ним запросы. Третий вариант — положить JSON текстом в обычный столбец; но тогда база не сможет выполнять запросы к его содержимому.

Текст В примере 2.1 region_id и industry_id — идентификаторы, а не строки вроде "Greater Seattle Area". Почему? Стандартные списки дают единый стиль написания, снимают неоднозначность при одинаковых названиях городов, упрощают модификацию, локализацию на другие языки и поиск: можно закодировать, что Сиэтл находится в штате Вашингтон, чего из строки не понять.

Текст По сути, хранить ID или текст — вопрос дублирования. ID не значит ничего для людей, поэтому его не нужно менять. А всё осмысленное может понадобиться изменить, и тогда придётся обновить все копии: лишняя запись и риск, что копии разойдутся. Идея исключить такое дублирование и лежит в основе нормализации. Эмпирическое правило из сноски автора: если значения, которые могут храниться в одном месте, у вас дублируются, схема не нормализована.

Переход Но у нормализации есть цена, и платит за неё именно документная модель.

11Многие-к-одному

Нормализация требует соединений — а их нет

Много людей живёт в одной области. Это «многие-к-одному», и оно плохо ложится на дерево

Реляционная БД: соединяет база
SELECT u.first_name, r.region_nameFROM users uJOIN regions r ON r.id = u.region_idWHERE u.user_id = 251;
Документная БД: соединяете вы
// соединение эмулируем в коде приложенияconst user = await users.findOne({ user_id: 251 });const region = await regions.findOne({  id: user.region_id,});
Сегодня
На момент книги MongoDB соединений не поддерживала. С версии 3.2 есть $lookup ↗

Текст Нормализация требует связей «многие-к-одному»: много людей живёт в одной области или работает в одной отрасли. В дерево такое не вписывается. В реляционных базах ссылаться на строки других таблиц по ID — норма, соединения выполняются легко. В документных для деревьев соединения не нужны, поэтому их поддержка часто слабая.

Текст Если СУБД соединения не умеет, приходится эмулировать их в коде приложения несколькими запросами. Работа, которую делала база, просто переезжает к вам.

Как показывать Код на слайде — моя иллюстрация, в книге этого примера нет. Сноска книги о поддержке соединений устарела: она описывает MongoDB на момент написания, а $lookup появился в версии 3.2 (2015).

Переход И дальше становится хуже: связи имеют свойство нарастать.

Источники MongoDB — $lookup.

12Связи нарастают

Новые фичи превращают строки в сущности

Компании и школы

organization был строкой. Нужны логотип, страница, лента новостей — значит, нужна ссылка на сущность

Рекомендации

Автор сменил фото — оно должно обновиться во всех рекомендациях. Значит, рекомендация ссылается на профиль

Текст Даже если первая версия приложения идеально подходит под документы без соединений, связи данных имеют обыкновение усиливаться. Два примера из книги.

Текст Первый: компании и школы. Сейчас organization — просто строка. Но захотели страницу компании с логотипом и лентой новостей — и строка становится ссылкой на сущность. На снимке LinkedIn видно: название Microsoft уже открывает карточку компании. Второй: рекомендации. Если автор рекомендации сменил фото, новое фото должно появиться во всех его рекомендациях. Значит, рекомендация должна ссылаться на его профиль.

13Рис. 2.4

Дерево стало сетью

Внутри пунктира — документы. Снаружи — общие сущности, которые будут соединяться при каждом чтении

Текст Вот что получилось. Внутри каждого пунктирного прямоугольника данные всё ещё можно сложить в один документ. Но компании, школы и другие пользователи должны быть именно ссылками — и потребуют соединений при запросах. И заметьте: один профиль теперь ссылается на другой через рекомендацию. Дерево превратилось в сеть.

Как показывать Схема как рис. 2.4. При наведении на узлы и зелёные стрелки — подсказки.

15Сетевая модель · CODASYL

Программист как навигатор

У записи теперь несколько родителей, а ссылка — это указатель на диске. К записи ведут только пути доступа от корня

Цена
Поменялся запрос — ручной перебор кода под новые пути. Не знаете пути — вы в тупике

Текст Сетевую модель стандартизировал комитет CODASYL. Это обобщение иерархической: в дереве у записи ровно один родитель, а здесь может быть несколько. Например, одна запись "Greater Seattle Area" и ссылки на неё от всех, кто там живёт. Так появляются «многие-к-одному» и «многие-ко-многим».

Текст Но ссылки здесь не внешние ключи, а скорее указатели, хранящиеся на диске. Единственный способ получить запись — идти от корня по цепочке ссылок. Такой путь и называется путём доступа. В простом случае это обход связного списка. Но к одной записи может вести несколько путей, и программист должен держать их все в голове. Даже члены комитета сравнивали это с навигацией по n-мерному пространству данных.

Текст В 1970-х, с магнитными лентами и их медленным поиском, ручной выбор путей позволял выжать максимум из железа. Но код получался сложным и негибким: если нужного пути нет — вы в трудном положении, а чтобы его поменять, надо переписывать горы кода запросов вручную.

Как показывать Схема на слайде — моя иллюстрация идеи, а не рисунок книги. Точки показывают два разных пути к одной записи.

20Гибкость схемы

«Без схемы» — миф: схема есть, просто при чтении

Schema-on-read
Как JavaScript

Структура неявна, её предполагает код при чтении. База ничего не проверяет. Динамическая типизация

Schema-on-write
Как TypeScript

Схема явная, база гарантирует, что всё записанное ей соответствует. Статическая проверка

Автор
Как и в спорах о типизации, правильного ответа нет. Термин «бессхемная» вводит в заблуждение: читающий код всё равно ждёт определённую структуру

Текст Большинство документных баз, а также реляционные базы с JSON не навязывают схему данных в документе. Такие базы называют бессхемными, но это вводит в заблуждение: читающий код всё равно предполагает определённую структуру. Схема есть, просто неявная. Точнее говорить schema-on-read, схема при чтении, в отличие от schema-on-write, схемы при записи, когда база гарантирует соответствие.

Текст Автор проводит аналогию с языками: схема при чтении — как динамическая проверка типов во время выполнения, схема при записи — как статическая при компиляции. И как в спорах о типах, правильного ответа нет.

21Смена формата

Делим name на имя и фамилию: две стратегии

Документы: дописываем код чтения
if (user && user.name && !user.first_name) {  // В документах до 8 декабря 2013  // поля first_name нет  user.first_name = user.name.split(" ")[0];}
Схема: выполняем миграцию
ALTER TABLE users  ADD COLUMN first_name text;UPDATE users  SET first_name =    split_part(name, ' ', 1);
Миф

ALTER TABLE — это простой? Обычно миллисекунды. Исключением в книге была MySQL: копировала всю таблицу

Реальность

Медленный — UPDATE всех строк в любой базе. Выход: оставить NULL и заполнять при чтении

Текст Допустим, полное имя лежит в одном поле, а мы хотим хранить имя и фамилию отдельно. В документной базе просто начинаем писать новые документы и добавляем код, который обрабатывает старые. В базе со схемой делаем миграцию: ALTER TABLE и UPDATE.

Текст Об изменениях схемы говорят как о медленных и требующих простоя. Это не совсем верно: большинство реляционных баз выполняют ALTER TABLE за миллисекунды. Известное исключение в книге — MySQL: она копировала всю таблицу, что означало минуты или часы простоя, хотя для обхода есть утилиты. А вот UPDATE большой таблицы медленный везде, ведь переписывать надо все строки. Если это неприемлемо, можно оставить NULL и заполнять поле при чтении — как в документной базе.

Как показывать Сегодня в MySQL 8 добавление столбца обычно выполняется без копирования таблицы (ALGORITHM=INSTANT) — описание в книге относится к версиям её времени. В книге для MySQL другой вариант UPDATE: substring_index.

22Что выбрать

24Цена локальности

Текст Локальность выигрывает, только когда нужны большие части документа сразу. Базе обычно приходится загружать весь документ, даже если вам нужен маленький фрагмент. При обновлении тоже обычно переписывается весь документ, а «на месте» можно сделать только изменения, не меняющие закодированный размер.
